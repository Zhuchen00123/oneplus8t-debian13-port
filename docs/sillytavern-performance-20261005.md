# 手机酒馆会话卡死与预热优化（2026-10-05）

用户实际验收发现“能进首页、点会话卡死”，因此此前HTTP接口通过不能视为浏览器验收完成。手机端已修复两处摘要预热生命周期/作用域缺陷，并改用有界批量计数。用户随后在Chrome确认能进入和正常切换会话；最后清理临时诊断后的刷新、输入与常用扩展按钮仍等待单独确认。Azure反代、原酒馆和MC通道没有参与本次性能修改。

## 已部署的变更

- 旧会话预热取消后，原实现可能留下“pending但promise已完成”的状态；等待循环不断await已完成promise，形成微任务饥饿。取消现在有终态，错误/旧作用域明确拒绝；源码Worker回归复现了原缺陷，7项等待/取消测试通过。
- 原刷新逻辑只检查pending，可能把取消或属于另一会话的任务当成可用缓存，对新会话重新发起同步逐条计数。现在同时检查会话身份、消息数组、tokenizer设置和当前计数文本；未准备好的范围先异步预热，生成拦截仍等待正确范围，不使用旧记忆注入。6项作用域回归通过，原就绪注入行为保持。
- 新`/api/tokenizers/openai/count-batch`复用原单条计数实现，每批最多128段、512KiB，客户端最多2批并发；写入同一原生按会话缓存。端点沿用登录、白名单和CSRF，不放宽访问控制。重复预热不请求，取消任务不请求，超限返回400。
- 未升级酒馆或扩展版本，没有删除聊天、世界书、摘要、向量或关闭插件；没有修改用户的上下文/记忆预算来换速度。补丁只在手机应用生效。

## 实际验证及限制

| 检查 | 结果 |
|---|---|
| 同一计数样例批量与原端点 | 逐项一致；这是既有tokenizer策略，不是提供商账单token证明 |
| 真实旧会话计数 | 1,142条消息、1,693段计数文本，从逐段请求合并为14次；手机本地约0.47秒，真实CNB公网路径约1.54秒 |
| 缓存复用 | 随后原同步计数零缓存漏查；重复预热零请求 |
| 4.7MB旧聊天读取/JSON解析 | CNB约2.65–2.75秒；Chrome的gzip/deflate/br/zstd协商也读到完整1,143条记录 |
| Chrome人工复验 | 用户确认已能进入、正常切换会话；脱敏计时记录1,585条消息完成加载/回调约3.65秒 |
| 运行状态 | 手机新增服务正常；未重启整机，未做长期高负载或温升验证。最后巡检另发现既有`kebab-powerkey-screen.service`失败，按用户禁止改动要求只记录，未修改/重启该服务 |
| 浏览器自动化 | 用户已授权，但控制连接持续失败，不能把人工确认描述为代理截图/自动化通过 |

临时阶段计时、错误类型/版本识别脚本与端点已移除，原核心自定义逐字保留；原始计时只保存本机受限私有目录。优化后的JavaScript需要刷新加载，清理前打开的旧页面不会自动替换已运行代码。

数据复核：36份聊天都存在。35份来源消息正文/角色标记/swipe逐项一致；另一份从1,573条增至1,585条，尾部有13个显示标记、2条正文及1个swipe列表变化，所有原swipe保留。不能推断这些运行后的变化全部由用户或某一个扩展造成；本轮性能脚本没有写聊天或设置，也没有用旧快照覆盖新数据。变化前原件仍在19:05的一致性私有来源归档。

性能数字只是这次有限测试，不能推断长期稳定或所有设备相同。模型、摘要和嵌入网关仍在Azure；网页可操作不表示长提示词推理、记忆质量或模型排队已全面优化。本轮没有新增付费生成压测。
