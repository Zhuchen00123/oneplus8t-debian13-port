# GDUT Wi-Fi 首次接入（2026-10-04）

用户要求手机直接连接大学城/番禺校区 `gdut`，再准备远程访问。内核保持 `7.2.0-kebab-debian13-r2+`；本轮没有刷分区、改 USB 地址或登录密钥。

## 当前结果

- ath11k_pci / QCA6390 设备存在，无 rfkill 软/硬阻断；iw/rfkill/wpa_cli 位于 `/usr/sbin`，普通 SSH 的 PATH 不含该目录，不代表工具缺失。
- 实际扫描到六个 `gdut` AP，最强约 -48 dBm，目标网络无 RSN/WPA 加密。
- 新建权限 600 的 `wpa_supplicant-wlan0.conf`，仅包含公开 SSID、`key_mgmt=NONE`、`country=CN`、`update_config=0`；没有账号或密码。
- 接口专用 `wpa_supplicant@wlan0` 已启动并启用，wpa_state=COMPLETED，实际关联为 5 GHz；systemd-networkd 获得 IPv4、IPv6、默认网关及 DNS。USB 管理链路仍通。
- 认证前 HTTP 请求被网关 302 重定向到学校登录页，HTTPS 超时；不能将已连接 Wi-Fi 当作已认证互联网。

## 用户认证入口

[学校无线指引](https://nic.gdut.edu.cn/info/1029/2396.htm)要求连 `gdut` 后用统一身份账号完成网页认证。[校区入口说明](https://nic.gdut.edu.cn/info/1029/2401.htm)列出大学城/番禺为 `10.0.3.2`，龙洞/东风路为 `10.0.3.6`。本机实际访问前者得到 Dr.COM 登录页。

手机尚无浏览器，因此已准备私有 `local/wifi-gdut-20261004/Open-GdutLogin.cmd` / `.ps1`：用户运行后，用严格 USB SSH 建立仅监听本机 loopback 的 SOCKS 代理；先核对登录页所见来源等于手机 Wi-Fi 地址，再用独立 Chrome/Edge profile 打开原始学校认证页。用户在学校网页输入密码，工具不代填或保存认证凭据到项目文件；浏览器 profile/原始证据均只留忽略的 local。

首个启动指引依赖 pwsh，但用户终端无此命令。现已兼容系统 Windows PowerShell 5.1，完整 `-CheckOnly` 预检通过，包含代理监听进程归属、手机地址、门户来源与退出清理。cmd 只对所启动的 PowerShell 进程使用 ExecutionPolicy Bypass，不更改系统执行策略。

前次代理 curl 测试因主机 NO_PROXY 绕过代理，不能作为手机证据。强制 socks5h 并清空该请求的 no-proxy 后，已核对正确来源；错误来源页面已删除。辅助脚本语法通过，代理端到端页面读取已验证。浏览器实际登录仍需用户完成。

## 待验收

门户认证、外网 HTTPS、DNS、NTP、断线/重启后认证状态、24 小时无线稳定性及远程穿透均未完成。不安装自动重登录/凭据持久化或穿透客户端，直到完成实际联网和用途确认。

私有原始证据入口 `local/wifi-gdut-20261004/`。AP、地址、校园账号、浏览器 profile 与原始门户内容不上传 GitHub。若需要撤销该关联，停止并禁用 `wpa_supplicant@wlan0`，保留配置供审计；USB SSH 不受影响。
