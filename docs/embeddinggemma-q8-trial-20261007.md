# EmbeddingGemma 2 ONNX Q8 手机试跑（2026-10-07）

Git发布增补：用户随后明确授权提交和推送。本地实施提交`8b2fd1c`；独立公开历史已推送[主题分支](https://github.com/Zhuchen00123/oneplus8t-debian13-port/tree/codex/embeddinggemma-q8-trial-20261007)，公开提交`d8ae2f5`，远端SHA一致。公开文件集与65个提交blob审核通过，不含模型权重、样例图片、原始报告或私有旧历史；main未合并。详见[发布记录](git-workflow.md)。

结论：KB2000 / Debian 13 能实际运行 ONNX Q8 文本与视觉嵌入。普通大核 CPU4 单线程的小样例测试中，短中文查询约0.59秒、128 token约1.57秒，低视觉预算下图片约8秒一张；适合低并发文本检索和后台图片索引。不是长期温升、完整多模态性能或生产服务验收。

## 部署与来源

- 当前内核实读 `7.2.0-kebab-debian13-r3-slider+`，aarch64。测前约11GiB内存、9.7GiB可用，/srv约214GiB可用，系统根约2.3GiB可用。
- 新建隔离目录 `/srv/embeddinggemma-q8-trial-20261007`，普通用户debian运行。复制Node20.20.2作为独立运行时；固定Transformers.js4.3.1、onnxruntime-node1.30.0，NPM安装使用`--ignore-scripts --omit=dev`，ARM64原生库实际可加载。
- 模型为[onnx-community/embeddinggemma-2-ONNX](https://huggingface.co/onnx-community/embeddinggemma-2-ONNX)，固定提交 `daa72c51243991dfcaf9f9137d2c573d8f7790c0`，只下载Q8文本、视觉权重与配置/分词器。主机按来源大小及LFS SHA-256检查，传输后手机所有选定文件大小与SHA-256逐项相同。清单在`config/embeddinggemma-q8-model-manifest.json`。
- 图片为[Xenova/transformers.js-docs](https://huggingface.co/datasets/Xenova/transformers.js-docs)的cats.jpg与corgi.jpg，固定提交 `542437c29cc5273cfd29e25c77696f2b349badd7`。两个样例hash及下载URL见`config/embeddinggemma-q8-sample-manifest.json`。
- 推理关闭远程模型下载，音频编码器禁用；未安装常驻HTTP服务、开公网端口或修改酒馆嵌入配置。私有原始报告在`local/embeddinggemma-q8-20261007/`。

## 已通过的实际功能

文本与视觉测试都实际产生768维有限、单位范数向量；中文查询在3份合成文本中两次找到预期文档。两个不同图像的向量余弦约0.6715，排除了同向量假成功；中英文各两条查询均在猫/狗两张图片中选择正确对象。

这仅是小样例功能冒烟：没有复现MTEB等官方评测、测真实个人资料或证明中文检索质量普遍提高。没有读取或发送私有聊天/截图，没有改动1024维旧向量索引。

## 性能与占用

推荐候选短测：CPU4单线程、inter-op1、Nice10，请求之间主动等待5秒；延迟不包含等待和首次模型加载。CPU4最大频率2419.2MHz，属于普通大核，没有使用2841.6MHz的CPU7。两次平衡模式测试分别运行约32.6秒和35秒，均正常退出。

| 场景 | 单次预处理+推理 | 说明 |
| --- | --- | --- |
| 中文查询，17 token | 0.587秒 | 一条查询；本轮首次推理，不代表平均延迟 |
| 3份文本，填充至26 token | 1.057秒/批 | 小样例批量建库 |
| 2条中文查询，填充至17 token | 0.710秒/批 | 功能验收查询 |
| 文本，32 token | 0.756秒 | 预处理较长原文后截断，非纯推理时间 |
| 文本，128 token | 1.567秒 | 同上；纯推理约1.481秒 |
| 猫图，640×480 | 7.918秒 | 图像预算70，实际含占位符67 token |
| 狗图，614×410 | 8.072秒 | 同预算，实际64 token |
| 4条跨模态文本查询 | 0.940秒/批 | 图片向量已存在后再查，不重算图片 |

| 指标 | 文本模式 | 文本+视觉模式 |
| --- | --- | --- |
| 进程峰值RSS | 743.1MiB | 1170.7MiB（约1.14GiB） |
| systemd cgroup峰值内存 | 531.8MiB | 791.7MiB |
| 采样CPU热区最高 | 61.6°C | 55.8°C |
| 采样电池温度最高 | 38.0°C | 38.1°C |

RSS包含进程映射/共享页，与cgroup计量不同，不能把两列指标混用；额外依赖、独立Node和下载缓存使试验目录总占盘约1.4GiB。测后/srv剩约212GiB、内存可用约9.7GiB。所有温度仅为离散传感器采样，没有测接口表面温度，不能证明长期热安全。

## 未通过或受限制的试验

1. 初始未限制CPU亲和的两线程测试：短请求约0.32秒，32 token纯推理约0.33秒，但连续请求时CPU7-top采样74°C，超过本轮自定65°C短测停止阈值。脚本退出码1并释放模型，未视为整轮通过；首轮峰值RSS559.6MiB。后续无负载CPU最高采样已回落到约51.5°C。
2. 小核CPU0–3范围单线程、每次间隔3秒：全部文本功能测试通过；32 token约3.9–4.0秒，128 token约8.05秒，512 token约28.4–28.5秒。CPU采样最高45.7°C、电池最高38.3°C、峰值RSS775.5MiB，但即时查询偏慢。
3. 小核视觉140预算：第一张猫图耗时88.1秒，运行RSS约1137.9MiB；第二次图像调用中主动停止临时单元，整轮没有完成跨模态验收。systemd在SIGTERM停止时显示result success只是停止流程状态，不能当作模型测试通过。

随后采用普通大核单线程、缩小图片预算、限制短测长度的配置获得前述实际通过结果。没有修改CPU调频、系统热策略、充电、电源键、USB SSH、分区、内核或既有基础监控。短测停止阈值是本轮的保护条件，不能当硬件安全规范。
